# V1 versus V2 on the arena Raspberry Pi

**Decision, 22 November 2026. Choose Option A. Refactor the working server in small releases.** A separate V2 becomes worthwhile if a measured limitation remains after the targeted corrections, or if an approved hardware or game requirement cannot be expressed safely through the existing host.

“V1” refers to the current working tree of LazerTag-V2, whose web app already reports `2.0.0-rc.2`. “V2” below means the proposed independent replacement in `LazerTagServerV2`. Both options have the same compatibility bar and use the existing Pi, ESP32 firmware, taggers, phones and TV. [Current release identity](LazerTagWebServer/LazerTagWebServer.csproj#L9) · [Audit and verification results](SERVER_CODE_AUDIT.md)

## What determines the decision

A local two-player run reproduced the exact registration failure. A missing ACK from the first player let a replacement take Team 2 after another tagger had already confirmed on Team 2. The failure begins at one use of collection count as identity. A second run reproduced a lost first `RCV` at the boundary between two readers. A third reproduced a fully reported match going from rank 1 to rank 0 solely because the operator finished debrief before the engine's next tick. Each failure has a small testable boundary, and each could recur in a clean implementation. [Join allocation](LazerTagHostLibrary/HostGun.cs#L739) · [Handshake handoff](LazerTagHostLibrary/LazerTagSerial.cs#L340) · [Scoring and rank publication](LazerTagHostLibrary/HostGun.cs#L2246)

The current server already has a single Pi process, bounded player capacity, locally served browser assets, efficient packet batching, per-device debrief acknowledgments, immutable completed-game files and a release rollback path. It has meaningful automated coverage of real HTTP and loopback relay paths, including an idle TCP failure during a live game. A rewrite would have to rediscover or characterize the gaps between standard and enhanced taggers, late acknowledgments, self-echo and noisy reports. ## Side-by-side comparison

| Decision factor | A · Optimize current host | B · Independent new host |
|---|---|---|
| Pi 3 performance | Already uses workstation GC and client-side clocks. Remove duplicate snapshots, bound relay buffers and measure. The data set is at most 24 players. | A deadline-driven loop and cached projections may reduce work. With the same game, .NET runtime, radio and browsers, the achievable benefit is unknown. |
| Live-game reliability | Roll out seat binding, finalization and relay framing one at a time. Existing tagger quirks and tested reconnect behavior carry forward. | A single writer and replayable events simplify reasoning. Every timing path, partial report and restart transition starts with an unproven implementation. |
| Development complexity | Local changes and a small number of cross-cutting state changes. The shared .NET Framework caller constrains library changes. | Parallel game engine, full public/admin contract, simulator, parity fixtures, Windows/data compatibility, hardware acceptance and cutover. Both systems require support until retirement. |
| Hardware and data compatibility | Highest initial confidence. Keep wire codec, numeric mode IDs, files, JS routes and device-specific behavior. | Highest initial risk. Subtle differences can pass normal desktop tests yet strand a tagger at assignment or debrief. A single ESP32 accepts only one controlling connection. |
| Maintainability | Improve the current boundaries gradually. Replace position-indexed setting arrays and the duplicated state descriptions behind stable interfaces. | An immutable roster, pure scorers and one state owner are easier to extend. Value arrives only after equivalence to existing editions, fixtures and operations has been demonstrated. |
| New modes and equipment | Add a tested strategy to the existing catalog, scorer and relay adapter. Existing modes expose where these definitions must agree. | A mode descriptor, scorer registry and adapter boundary offer cleaner extension points. A new feature dependent on absent tagger data still needs a verified hardware capability. |
| Expected CPU | Main costs to investigate are periodic full snapshots, polling, logging and the active 100 ms tick. Event-driven publication can be applied directly. | Reduced idle wake-ups are plausible. IR pulse generation stays on the ESP32, so a reimplementation cannot shorten its required wire timing. |
| Expected RAM | One CoreCLR/Kestrel process, a small roster, two transport workers for active TCP, browser connections and transient views. Peak RSS and SD-card effects have not been measured. | The same runtime and public interface imply a similar baseline class. A bounded queue can cap growth. New serializers, event buffers or a resident second process can raise peak RAM. |
| Long-term stability and servicing | Move the Pi to a supported LTS independently of game fixes. Continued work on one production line and the existing rollback mechanism lowers operational burden. | Independent releases isolate experiments and permit shadow replay. Divergent protocol behavior, two history writers and duplicate relay ownership become explicit operational risks. |
| Time to accountable evidence | The existing fixtures and specific failing scenarios make the first corrective release independently testable. | The first useful milestone is a byte-compatible simulator and differential replay. A replacement provides no production benefit until the full acceptance gate is met. |

The concrete bases for the resource comparison are a one-second periodic broadcast while hosting with clients, two HTTP fetches per browser every five seconds, and a complete roster projection for each state build. These are source-derived workloads. At a full 24-player roster, the hits projection alone visits up to 576 player/target pairs per snapshot. Both options retain a managed runtime and should be held to the same provisional budget of 25% of one core in steady play and 180 MiB steady server RSS. These are acceptance targets. No Pi CPU/RAM baseline or running V2 was measured. ## Decision gates

1. **First V1 release.** Fix the reproducible registration, end/force and handshake defects behind regression tests. Keep the venue on its current release while developing. Package runtime servicing as a separate candidate to make a failure attributable.
2. **Measure on the Pi.** Replay the same seeded matches and client counts on the baseline and candidate. Record CPU, RSS, event-to-state latency, browser convergence, reconnect times and a 24-hour soak. Include the local Chromium kiosk separately if that is how the venue runs the TV.
3. **Continue with A when it meets the gates.** Preserve the measured traces and tests. Introduce the proposed single state owner and smaller projections only where they remove a demonstrated failure or measurable cost.
4. **Reopen B only on evidence.** Examples include a reproducible resource-budget miss after targeted optimization, an approved new equipment interface that cannot be isolated, or recurring incompatible state transitions despite the characterization suite. An offline V2 prototype should demonstrate a material measured gain or resolve that specific blocker, pass the entire compatibility matrix, and successfully rehearse rollback before replacing V1.

The development plan specifies the independently testable design, performance thresholds and rollback rehearsal that make this decision reversible. [V2 development and acceptance plan](V2_DEVELOPMENT_PLAN.md)
