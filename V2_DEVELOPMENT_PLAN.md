# Next-generation LTAR server development and verification plan

**Planning document · 22 November 2026 · Optimize V1 first.** This is a design and acceptance contract for a possible independent server. The simulator, protocol fixtures and measurement plan are also useful for improving V1. A future replacement would live entirely in a sibling `LazerTagServerV2` directory, with its own source, tests, build outputs, data and service identity. The baseline is the current working tree identified in the audit. [Audit](SERVER_CODE_AUDIT.md) · [Decision and reopening criteria](V1_VS_V2_COMPARISON.md)

## 1. Platform and proposed architecture

The repository targets Pi 3B/3B+, Raspberry Pi OS Lite 64-bit, Trixie/Debian 13, and a self-contained `linux-arm64` executable. The installer checks `uname -m` and the OS release. The existing ARM64 publish passed on the workstation. Record the actual arena model, `/etc/os-release`, `uname -m`, `dpkg --print-architecture`, available memory, active release ID, firmware build if known and whether Chromium runs locally at the start of a future hardware qualification. A 64-bit CPU alone does not establish the userspace ABI. [Pi deployment target](deployment/PI_SETUP.md#L3) · [Installer checks](deployment/install.sh#L99) · [Microsoft ARM deployment guidance](https://learn.microsoft.com/en-us/dotnet/iot/deployment)

Use a single ASP.NET Core/Kestrel process on a serviced .NET 10 LTS patch, with workstation GC, invariant globalization while the existing file formats support it, bundled static HTML/CSS/JavaScript and SignalR. Keep runtime and framework servicing in normal release builds. Publish and smoke-test the exact runtime and native dependencies on the intended OS. Debian 13 Arm64 is listed in the .NET 10 support matrix. Keep the existing Windows .NET Framework host building independently. |---|---|

Keep the game loop asleep until a real input or its next deadline. Use familiar .NET facilities such as a bounded channel, cancellation tokens, `TimeProvider`/monotonic timestamps, `System.Text.Json` and the existing logging abstractions. A broker, database server, container orchestrator and server-rendered TV frames have no demonstrated need for one arena. Old and candidate hosts may run against separate simulators, and offline replay can feed both. The real relay always has a single owner. ## 2. Compatibility contract for the deployed relay

### Network and outer messages

Production uses a Pi-hosted 2.4 GHz WPA2-PSK/CCMP hotspot. Defaults are SSID `LazerTag`, channel 6, `wlan0`, Pi/gateway/DNS `192.168.4.1/24`, DHCP `.20–.99` and relay static `192.168.4.100:8266`. The Pi listens for web clients on port 5000 and initiates the TCP relay connection. The sketch's station hostname advertised by mDNS is `lazertag.local`. The management examples use `lazertag-pi.local` or the management IP. Keep the fixed arena addresses usable when mDNS is unavailable. The firmware also has a compile-time AP variant, and the production profile uses station mode. On the default arena hotspot the operator opens the root page and the TV opens the dedicated scoreboard. The on-Pi kiosk uses loopback. [Operator console](http://192.168.4.1:5000/) · [TV scoreboard](http://192.168.4.1:5000/tv.html) · [Kiosk URL](deployment/xinitrc#L86) [Hotspot defaults](deployment/hotspot.conf#L4) · [Firmware roles and addresses](esp32_relay/sketches/RelayESP32/RelayESP32.ino#L32) · [mDNS](esp32_relay/sketches/RelayESP32/RelayESP32.ino#L385) · [Management access](deployment/PI_SETUP.md#L326)

ASCII, CRLF-terminated, one command per line. The firmware input buffer is 96 bytes including framing/storage overhead. The Pi currently accepts CR, LF and CRLF and has compatibility handling for concatenated legacy fragments. A TCP read or write can span any number of line boundaries. TCP uses no-delay and a single client. Lines, statuses and diagnostics must retain their case on transmit. [Firmware parser](esp32_relay/sketches/RelayESP32/RelayESP32.ino#L543) · [Host line splitter](LazerTagHostLibrary/LazerTagSerial.cs#L855) · [Legacy fragment handling](LazerTagHostLibrary/LazerTagProtocol.cs#L205)

| Direction and line | Exact meaning |
|---|---|
| Pi → relay `HELLO 1` | Decimal protocol version. Sent when TCP opens. Valid hello when relay ready establishes the session and returns `READY 1`. Other versions yield `ERROR BAD_VERSION`. |
| Pi → relay `PING` | Returns `PONG`. The parser handles this independently of the CMD-ready gate. The Pi currently probes after 5 s of quiet and gives a pending probe another 5 s. Received activity resets its idle timer. |
| Pi → relay `BYE` | Relay returns `OK` and closes the session. V1's normal transport disconnect can simply close the socket. Both endings must work. |
| Pi → relay `CMD 10 <data> <bits> <beacon>` | Four hexadecimal fields, including opcode 0x10. Beacon is 0 or 1. Data must fit its bit count. Non-beacon widths 7, 8, 9. Beacon widths 5, 9. Each accepted signature produces an individual `OK` after successful IR transmission, including when the Pi batches many lines into a single write. |
| Relay → Pi `READY 1`, `PONG`, `OK` | Handshake accepted, heartbeat response, and command/close acknowledgment respectively. There are no sequence numbers or tagger-delivery receipts in these lines. Preserve any following bytes already read with READY. |
| Relay → Pi `RCV <data> <bits> <beacon>` | Data and width are uppercase hex in the formatter, beacon is 0/1. Contains one received IR signature. It may be a self-echo. A 7-bit tag is observational. |
| Relay → Pi `RAW <type-character> <data-hex>` | Unclassified nonblank IR diagnostic. Keep available to diagnostics. It does not score a player. |
| Relay → Pi `ERROR <code>` | Implemented codes are `BAD_FORMAT`, `BAD_VERSION`, `NOT_READY`, `RELAY_NOT_READY`, `UNKNOWN_COMMAND`, `BAD_BEACON`, `BAD_BITS`, `BAD_DATA`, `TX_FAILED` and `LINE_TOO_LONG`. A line overflow closes the session. A partial outbound TCP write also closes it. Preserve diagnosis and reconnection semantics. |

The shipped sketch defines dispatch, validation, return values and output formatting. The host also tolerates legacy `OK Sent` input chatter. ### IR signatures, timing and packets

| Signature | Bits on air | V1 interpretation |
|---|---:|---|
| T | 7 | Address in upper five bits, tag strength derived as low two bits + 1 |
| Z / E | 5 / 9 | Standard zone/hit beacon or enhanced LTAR beacon. Beacon flag set. Preserve team, hit, shield/status or zone bits as encoded. |
| P / D / C | 9 / 8 / 9 | Header has bit 8 clear and the packet type in its low byte. Data is a succession of bytes. Checksum sets bit 8 and carries the low byte of type plus all data bytes, sum modulo 256. |

The reviewed sketch uses RX GPIO 15/channel 0 and TX GPIO 4/channel 1. RMT uses a 38 kHz carrier, 50% duty, microsecond ticks, 3000/6000 µs pre-sync mark/space, 3000 µs normal or 6000 µs beacon header, 2000 µs space and 1000/2000 µs zero/one marks, most significant bit first. End gaps are 25 ms by default, 56 ms for T and 80 ms for C. The receiver's comparison tolerance is 20%. These constants describe the source waveform. Beam coverage and actual tagger tolerances require physical observation. Firmware services receive before processing at most one input line each loop and uses blocking RMT writes so the waveform buffer remains valid. The candidate must accept this pace with the existing firmware. Any proposed firmware change requires separate owner authorization. [Timing constants](esp32_relay/libraries/ESP32_IR_LTTO/ESP32_IR_LTTO.cpp#L49) · [Carrier and blocking send](esp32_relay/libraries/ESP32_IR_LTTO/ESP32_IR_LTTO.cpp#L193) · [Bit order and gap splitting](esp32_relay/libraries/ESP32_IR_LTTO/ESP32_IR_LTTO.cpp#L477) · [Firmware loop](esp32_relay/sketches/RelayESP32/RelayESP32.ino#L205)

Packet IDs below are hexadecimal. Payloads list successive eight-bit data fields after the packet header and before the checksum. “Game” is the one-byte protocol match ID, “tagger” the one-byte physical join ID. Preserve separate durable GUIDs for history. For player address packing, team is one-based, local player slots are one-based and the encoded slot field is slot minus one. 2:3 shifts team by three bits, 4:4 by four, and 3:4 masks the high reply bit for the single-tag diagnostic. [Packet type enumeration](LazerTagHostLibrary/Packet.cs#L143) · [Checksum](LazerTagHostLibrary/Packet.cs#L114) · [Address packing](LazerTagHostLibrary/Player.cs#L190)

| Packet ID and direction | Payload and compatibility behavior |
|---|---|
| 02–0B, 0C · host advertisement | Game, minutes, HP/tags, reloads, shields, mega, flags1, flags2. The five numeric settings use packed decimal, with 0xFF retained where the field permits unlimited. 0C adds four padded game-code characters. Specific IDs appear in the modes table. |
| 81 · enhanced advertisement | Game, minutes, HP, reload rounds low/high, shields, mega, flags1, flags2, flags3, starting ammo, sleep minutes. Numeric bytes are binary. Limited reloads are clips × 10 in little-endian rounds, unlimited is FFFF. Nonpositive minutes/HP/ammo encode FF under the encoder's rules. Zero shields/mega encode zero. |
| 10 / 82 · tagger join | Standard accepts game, tagger, preferred team low two bits. Enhanced uses game and tagger, and tolerates extra tagger information. The current host ignores that optional information and uses the plan. |
| 01 / 83 · host assignment | Game, tagger, assigned address in 2:3 for both editions. A repeated request can resend the same assignment. |
| 11 / 84 · tagger assignment ACK | Game, tagger. Confirms the pending physical ID. A wrong game or absent pending join is rejected. |
| 0F / 8F · host assignment failed | Game, tagger. Used for capacity refusal or timed-out joins. Confirmed-rejoin timeout preserves the existing player. |
| 87 · enhanced host release | Game, address in 2:3. Used after assignment ACK, at countdown start for confirmed players, and once when that player's required debrief reports are complete. No release burst at summary entry. |
| 00 / 88 · host countdown | Game, seconds, three team fields. Standard uses packed-decimal seconds and byte counts 8,8,8. Enhanced uses binary seconds and per-team slot masks, bit 0 for slot 1. |
| 31 · host debrief request | Game, address, flags. Standard uses 4:4, enhanced 2:3. Bit 0 asks for summary, bits 1–3 for team groups. Solo uses three address groups for 24 players. Team modes request their declared group count. |
| 40 · tagger summary | Eight data bytes carry the game, address, tags taken, survival minutes, survival seconds, zone minutes, zone seconds and expected team-report flags. Numbers use the existing nibble decoding. Expected reports are indicated by bits 1–3. |
| 41 / 42 / 43 · tagger detail | Game, reporting player's address, eight-slot mask, one tag count for each set bit in ascending slot order. The type identifies the team that tagged the reporting player. Validate the complete length before applying. A valid zero mask is a received empty report. Duplicate detailed reports are ignored. |
| 32 · host rank | Game, team high nibble and rank low nibble, eight player rank bytes, zero-filled for empty slots. Solo broadcasts across the physical address groups with team rank zero. Preserve competition ties and the incomplete-result policy in the audit. |
| 48 / 80 / 90 · auxiliary | 48 accepts four data bytes. The receiver ignores the first, reads two 3:4 addresses with reply flags, and logs the count. 80 handles printable text and the sender limits it to ten characters plus a zero terminator. 90 logs the recognized special-attack identifiers in data byte 2 and other fields as diagnostics. Preserve the observed bytes and diagnostic behavior. |

Standard flags1 bits 7 through 0 are extended tagging, limited reloads, limited mega, team tags, medic, slow tags, hunt-the-prey and reverse hunt. Flags2 bits 7 through 2 are zones, team zones, neutralize in zone, zones revive, hospital zones and zones tag. Bits 1–0 hold the protocol team count. Enhanced flags1 carries team tags, medic, slow tags, hunt and reverse in bits 4–0. Respawn also sets flags1 bit 7 and flags2 bits 5 and 4 in both encoders. Enhanced flags3 uses bits 7, 6, 5, 1 and 0 for standard beacons, suppress IFF proximity beacons, suppress tag-received beacons, auto reload and full auto. Preserve the web-enforced medic-off rule. Preserve existing zero/reserved bits. Malformed checksums must not update the roster or results. Preserve self-echo filtering and the limited orphan recovery used in Summary. V1 buffers up to 16 orphan data signatures and only tries a candidate type implied by the selected player's pending report, subject to checksum and normal payload checks. The host accepts stable noncanonical counts such as 0x8A using its legacy nibble arithmetic (90), and handles 0xFF as 255. Golden traces must include these cases. ### Match lifecycle and recovery

| Phase | V1 behavior to characterize |
|---|---|
| Idle and start | Service checks standby connectivity after an initial 2 s, then on a 5 s cadence. A successful start validates the entire plan, releases standby, waits 500 ms and opens the hosting connection. A host is held in memory until cleanup. A new match has a new history GUID and separate eight-bit game ID. |
| Lobby | Announcement every 1500 ms. Individual overrides are broadcast for the upcoming seat before a tagger joins. Neither assignment packet carries HP, ammo or a player name. Preserve the guided power-on order and exercise two different overrides with overlapping join attempts. V1 currently uses join position, with the removal defect in the audit. Planned team takes precedence over a valid requested team, then smallest eligible team. First free physical address is assigned. Solo covers 1–24 across three groups of eight. Two teams allow 16 players and three allow 24. Teams must each be represented. Unconfirmed taggers occupy capacity. |
| Assignment | Wait 2 s for acknowledgment. On timeout, send up to six failure packets spaced 500 ms apart. Respect repeated confirmed joins, extras, missed ACKs and the distinction between a reservation and a confirmed player. The service blocks countdown until the relay is online and all planned entries are present, confirmed and valid. |
| Countdown and play | V1 polls the engine every 100 ms and emits decrementing countdowns about once per second. Locked settings and realized teams carry into play. A library resend countdown preserves the original game end and defaults to 10 s. Resend is a library operation. The phone exposes countdown, end and clear. Timed end or operator End in Playing enters Summary. |
| Zones and roles | Contested Zone uses a team-0 five-bit zone beacon with value 2. Respawn uses team-0 supply/team-zone value 3. Both repeat at about 500 ms. Hide and Seek/Hunt the Prey display 60 s role cycles. The hardware enforces play. |
| Debrief and GameOver | Cycle incomplete players, one directed request every 6 s. Summary plus the groups it declares must be present. Enhanced releases after that player's completion. Complete games calculate scores/ranks once and cycle rank packets roughly every 3 s. Incomplete force-finishes retain diagnostics. The B2 correction needs explicit wire acceptance on the physical taggers. |
| Reset and restart | End during lobby/countdown discards the unstarted session. From GameOver the phone's New Game/next or cleanup discards active state, clears hints, timestamps and rosters, and restores standby behavior. A browser refresh fetches the latest phase. TCP recovery in the same process retains the match. After process death V1 starts Idle. A future interrupted-match record may aid the operator, but automatic mid-match resumption would need tagger-level evidence. |
| Transport timeouts | TCP defaults are port 8266, 3 s connect timeout, five attempts with 1 s between, 2 s handshake, 500 ms read timeout and 2 s write timeout. Hold the one-owner constraint during reconnect. Legacy direct serial uses 115200 8N1, no flow control, DTR/RTS enabled, and a 50 ms delay per write-queue item. The shipped sketch uses USB for diagnostics. |

### Exact scoring baseline

- **Effective hits** sum `min(max(rawHits, 0), max(targetHP, 0))` for each eligible target. Exclude self, dropped targets and same-team targets in team play. An individual HP override takes precedence. Detailed reports populate both scorer and target matrices. The HP cap also applies to Respawn in V1. Characterize repeated lives before changing that rule. [HostGun.CountEffectiveHitsScoredCore](LazerTagHostLibrary/HostGun.cs#L295)
- **Custom/Respawn solo** use effective hits as the player score. **Battle/role/Respawn teams** use effective hits per player. If any team has survivors, a team's score is `1024 × survivors + 4 × sum of surviving players' scores`. When no team has survivors, team score is its total player hits. A player counts as surviving when reported survival duration is at least the configured match duration. [Scoring](LazerTagHostLibrary/HostGun.cs#L1156) · [Survival flag](LazerTagHostLibrary/HostGun.cs#L928)
- **Survival** gives each player effective hits plus ten points per whole survival minute. Team score is `1024 × survivors + 4 × sum of survivors' player scores`, including the all-zero result when everyone is eliminated. **Own the Zone** scores one point per reported zone second and sums member scores per team. [Survival](LazerTagHostLibrary/HostGun.cs#L1295) · [Zone](LazerTagHostLibrary/HostGun.cs#L1143)
- **Kings** gives a player +1 for each raw tag on an opposing King and −4 for each on their own King. Team score is `1024 × kingSurvived − 4 × tags taken by the King`. Test negative totals and hidden King identities. The source itself flags the formula for hardware comparison. [Kings scorer](LazerTagHostLibrary/HostGun.cs#L1212)
- **Ranks, drops and result provenance** use descending competition ranks such as 1, 1, 3. V1 removes dropped-player hit contributions before natural scoring. Forced/incomplete history is diagnostic, and both browser views withhold winner claims. Capture exact rank bytes and raw report masks in replay fixtures. Schema-v1 history stores per-player effective settings, hits, scores, ranks and early/forced flags. It omits the raw hit matrices and survival/zone times, so history alone cannot reconstruct every scoring input. Preserve historical readers. Document approved B2 behavior as a deliberate correction in the parity ledger. ## 4. Proposed phone and TV design

**Phone.** Put the current match phase and relay status at the top, followed by mode and roster during setup. Show a single primary action for the current phase. On the roster, show planned name/team, pending assignment, confirmed slot and the exact blocker, such as “Waiting for Team 1's tagger to confirm.” Keep individual overrides behind each player row, presets and history accessible, and the current draft across a recoverable network failure. Separate ordinary end from forced partial completion. A New Game reset becomes available after results are archived or their pending status is visible. Use text as well as color, large tap targets and accessible focus behavior. A hardware-wide pause has no verified command or clock synchronization in the current protocol. Leave the live control out of the candidate until a separately approved design proves all tagger clocks can stay aligned. [Existing phone controls](LazerTagWebServer/wwwroot/index.html#L93) · [Current end confirmation](LazerTagWebServer/wwwroot/js/app.js#L1333)

**TV.** Give countdown and remaining game time the largest type. During play, show team rosters, objective, active zone or 60-second role cycle. During debrief, show per-player receipt progress and distinguish absent, dropped and complete reports. As authoritative data becomes available, show team and player results with shared ranks and visible incomplete status. The present taggers do not provide an authoritative continuous arena-wide live hit feed. Keep live tag totals out of competition standings until a supported equipment capability supplies them. Drive local time from the latest server offset, update only changed DOM nodes, retain the last valid screen during reconnect and rehydrate from a full versioned snapshot on refresh. Test readability from the actual viewing distance, in the maximum roster and tie layouts. ## 6. Acceptance criteria and measurement method

These numbers are **proposed acceptance targets**. On-device results will come from the matched runs below. Use the same Pi, OS image, SD card, power, cooling, relay, browser versions, snapshot workload, release settings and room layout for A/B runs. Record at least three warmed repetitions with a cold start measured separately. Keep browser and server timings on their own monotonic clocks. For cross-device latency, synchronize/test clock offset or use a round-trip acknowledgment with a reported uncertainty. Report p50, p95, p99, worst case and sample size.

| Measure | Repeatable workload and proposed pass gate |
|---|---|
| CPU | With 24 planned taggers, 8 phone tabs and one TV, sample service CPU every second for 15 min per phase. 100% means one fully occupied core. Mean idle ≤5% of one core, mean steady play ≤25%, p95 in busy debrief ≤60%. Measure no-client idle separately. Record CPU of the optional local kiosk separately and check for thermal throttling and swap pressure. |
| Memory and bounds | Sample RSS, managed heap, allocation rate, queue age/depth and whole-device available memory. Target steady web-process RSS ≤180 MiB, peak ≤220 MiB, and ≥150 MiB system memory available in the intended topology. Limit RAM for pending history, log queues and each client. Any deliberate coalescing must use a measured counter and preserve critical events. |
| Game latency | Time last complete inbound frame to committed engine revision, excluding physical IR airtime. At representative traffic and a 2× burst, p95 ≤50 ms and p99 ≤100 ms. Require zero lost accepted critical game events. Compare outgoing countdown and beacon timing to V1 captures and verify normal tagger acceptance. |
| TV and phone freshness | Timestamp server state commit and browser-applied revision. Connected p95 ≤250 ms and p99 ≤500 ms for phase, roster and final results on the arena LAN. During play local timers stay within one second of the reference after synchronization. A refreshed page shows the correct phase and roster within 2 s of a usable connection. No stale revision ever replaces a newer one. |
| Relay recovery | In lobby, countdown, quiet play, zone play and debrief, repeat clean disconnect, silent peer and Wi-Fi loss. Flag a silent peer within 12 s and restore READY within 15 s of its return to listening under the defined LAN test. Keep match ID, roles, seats and original deadline in every same-process recovery. No duplicate assignment, automatic forced result or stale countdown replay. Hardware-deaf intervals are recorded explicitly. |
| Score correctness and throughput | Cover all 16 public modes, all applicable editions, 2/8/16/24-player boundaries where legal, and the six legacy XML entries in library tests. Use golden masks, partial/out-of-order reports, known noncanonical BCD, repeated lives, ties and negative Kings scores. Replay at least 1,000 seeded simulated matches and a 2× burst over the busiest recorded input. Require exact expected scores, ranks, team totals, byte-level replies, one history record per completed game and correct partial-result markings in every case. |
| Soak and failed storage | Run ≥24 h, at least 200 rapid simulated rounds, repeated browser reconnects and 100 injected relay disconnects. No crash, deadlock, unbounded queue, unobserved archival failure or sustained handle growth. After warm-up, comparable idle-window median RSS must stay within 10 MiB from first to final window, with no sustained growth above 0.5 MiB/h. Restore a delayed disk and account for every completed-match GUID. |
| Equipment and deployment parity | Record each owned tagger model/firmware when available, standard and enhanced joins, two teams and all three address groups, role swap, Kings IFF, Zone and Respawn, debrief/release and displayed ranks. Complete a physical round in each supported mode and exercise every device family in both applicable hosting editions. Untested combinations keep an open ledger entry. Cold boot, operator PIN, TV, saved data and rollback must work on the actual Pi. |

For measurements, use systemd process accounting or `pidstat`, `/proc/<pid>/status`, `/proc/meminfo` and concise structured timestamps. If managed counters require diagnostics, enable them only for an isolated benchmark profile and repeat the timing comparison in release configuration. The supplied production environment disables diagnostics. Physical captures and desktop simulations have separate evidence columns. [Production environment](deployment/lazertag.env.example#L3)

A replacement qualifies only after all correctness, compatibility, recovery and rollback gates pass. To call it materially more efficient, preselect a target such as a ≥20% relative reduction in busy-phase CPU or p95 state latency, reproduce it in three matched runs, and keep other measured resource and latency metrics within 10% of baseline or better. If V1 is already inside target and the candidate brings little operational benefit, continue shipping V1.

## 7. Build, deploy and rollback design

1. **Build in isolation.** In the future `LazerTagServerV2` checkout, CI would restore locked dependencies, build Release with analyzers, run unit, protocol, API, browser, replay and Linux packaging tests, then publish the Pi web project with `dotnet publish -c Release -r linux-arm64 --self-contained true`. Package the publish directory flat, record SHA-256 and a manifest including game XML, both HTML entry points, browser scripts, executable and runtime manifests. Validate ELF64/AArch64 and run a smoke test of the packaged output.
2. **Separate environments.** Use a candidate release root such as `/opt/lazertag-v2/releases`, separate config and data directories, a distinct service and a loopback-only preview port. The preview connects only to the simulator and uses copied settings/history. The existing LAN updater targets the V1 deploy helper. Give a candidate its own explicitly selected staging destination before using an uploader for it. Keep V1 backup and rollback tools available throughout.
3. **Qualify before cutover.** In an approved idle window record the exact known-good V1 release ID, take a data/config backup and verify that a restored copy opens. Check schema-v1 readability in both directions. Stop admissions and verify Idle, completed history written, and no active debrief. Only one process can own the real relay or public port. Switch ownership deliberately, verify the expected service/version/address, and then enable admissions. Stage future schema changes additively and retain old readers.
4. **Probe from all three sides.** Verify local readiness, the real mode catalog, PIN/status, history, public TV and client rehydration. Confirm READY and a real tagger join, debrief and rank during the acceptance window. A standalone `/healthz` response is insufficient for promoting a release.
5. **Roll back between games.** Stop candidate admissions, save completed candidate records and record any interrupted session. Release the relay and port, restore V1's original service/config/data pointers and select the recorded known-good V1 release ID. If the active V1 release link needs switching, its existing helper accepts an explicit `release-<id>`. Verify service version, operator, TV, relay, a join and old history before reopening. Preserve candidate history separately and reconcile by GUID with a tested importer. A hot switch cannot transfer tagger clocks or guarantee resumption of an in-flight match.
6. **Rehearse failure.** A deliberately incomplete staging package must fail readiness before admission. A candidate fault after a completed pilot match must permit V1 restoration within a proposed five-minute maintenance window, with both histories accounted for. Production promotion requires recorded evidence from this rehearsal. Until the measured decision gate calls for an independent server, the fixtures, four reproduced audit cases and Pi benchmarks are the highest-value work to carry into V1.
